# Tavo 主线最小开发

当结果是「具体改哪里、怎样最小改、怎样证明」时使用。方向未定时先比较方案并解决会改变结果的歧义，不强制启动其他技能、任务协议或审批机制。

1. **定目标。** 写出一个可观察变化及必须保持不变的行为。确认目标项目，不从 `Memory Center` 推断是旧记忆管家，也不把多个 TPG 当成单一包。
2. **找 owner。** 当前项目规则 → 最近合同 → 真实入口、调用方与 owning tests → 当前 `package.json`、builder 或对应的命令配置。只有当前运行时合同影响方案时才查对应官方页或授权发现。遇到归档或生成物，要回到维护源，不凭旧文件名猜测。
3. **锁最小范围。** 列出要改的文件、必须不碰的状态/接口、最小验收和回滚。每个文件由目标、当前合同或已证实的调用关系解释；未知或冲突的前提先核实。按直接证据/推断/未知区分关键结论。
4. **证明。** 行为变更优先建立能命中根因的回归；文档和配置走引用/结构/owner 检查；生成物由 owner 构建后再检查结果。新增依赖、权限、数据迁移、外部影响或 owner 漂移时重新核对范围，不把锁扩大成许可证。

只需交付 owner 与计划时不改文件。已授权实施时把锁交给实际源 owner，按现行项目门禁验收，不因需要构建就另开一套流程。[项目结构速查](../tavo-memory-steward-clean-workflow/references/project-architecture.md) 只帮助确定入口。
